# Authentication event format v1 - working design

Version 1 input is UTF-8 JSON Lines (.jsonl): each nonblank line is a complete JSON object. This avoids a large enclosing array and permits clear per-line error reporting. These requirements will be implemented and tested in the ingestion stage.

## Fields

| Field | Required value | Purpose |
| --- | --- | --- |
| event_id | Nonempty string, maximum 128 characters | Stable identifier supplied by the source; unique within the import source namespace. |
| source | Nonempty string, maximum 64 characters | Identifies the emitting application, such as local-login-lab. |
| timestamp | ISO 8601 datetime with explicit UTC Z or numeric offset | Time the event occurred; normalize to UTC. |
| source_ip | Valid IPv4 or IPv6 string | Source address observed by the emitting application. |
| username | Nonempty string, maximum 128 characters | Account being accessed; preserve case in v1. |
| event_type | login | Only login events are supported initially. |
| outcome | success or failure | Result recorded by the source. |

Unknown fields are rejected in v1 to catch typos and discourage accidental private-data ingestion. Blank lines are ignored and counted separately. Invalid records are excluded with line-specific errors. Original accepted records are preserved separately from normalized fields. Do not store attempted passwords, tokens, session cookies, or full authentication requests.

## Identity and ordering

Use (source, event_id) as event identity. Exact repeats are skipped; the same identity with changed content is rejected as a conflict. Canonical field values determine equality, so whitespace and JSON key ordering alone do not create a conflict. Input IDs are metadata supplied by the source, not proof that an event is authentic.

The importer preserves usernames exactly and does not assume that usernames are case-insensitive. Normalize IP text with an IP parser. Normalize timestamps to UTC and retain original input. Define supported timestamp precision before coding and test it consistently.

Sort accepted events by normalized event time for detection. An event ID may be used as a deterministic display tie-breaker, but must not be treated as proof of temporal order.

## Teaching example

```json
{"event_id":"demo-001","source":"local-login-lab","timestamp":"2026-09-24T09:00:00Z","source_ip":"192.0.2.10","username":"demo_user","event_type":"login","outcome":"failure"}
```

This is one recorded failed sign-in, not evidence of an attack on its own. The sample file in data/samples/day01_login_events.jsonl contains two failed attempts and one successful attempt for the same account/source. It is below all three default rule thresholds and should produce zero alerts once the engine exists.

The sample is synthetic. No network traffic, real login attempt, or attack is generated by reading it.
